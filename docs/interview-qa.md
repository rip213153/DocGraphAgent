# 面试 Q&A 知识库

这份文档不是源码导读，而是一份基于当前实现整理出来的面试答辩口径。目标有两个：

- 面试前快速通读，形成稳定、不夸大的回答框架。
- 面试中如果被深挖，能把“为什么这么做、现在做到什么程度、边界在哪里”讲完整。

文中的回答整体偏面试表达优先，但都尽量落在当前代码事实上。对于还没做到的部分，我会明确说是“下一步方向”，而不是包装成“已经实现”。

## 1. 工作流编排

### 为什么把入库和问答链路改成轻量状态机，而不是继续顺序调用

如果只看 happy path，顺序调用当然也能跑通：调 parser、调 extractor、写向量、写图谱，最后返回结果。这种写法在 demo 阶段很快，但最大的工程问题是它只能表达“做完了没”，很难表达“做到哪一步了、哪一步失败了、哪一步允许降级、哪一步重试过、失败后还能不能继续”。一旦链路变长、外部依赖变多、要补监控和排障，这种写法就会开始失去解释力。

我把它改成轻量状态机，本质上是把“流程进度”从隐含在代码顺序里的事实，提升成一个显式、可校验、可返回、可测试的工程对象。这样做有几个直接收益：

- 每个阶段的语义被固定下来，接口和日志里能明确看到当前走到哪一步。
- 合法迁移由状态机约束，不再依赖工程师脑内记忆“下一步应该调什么”。
- `retry`、`degraded`、`workflowState` 这些工程化信息能以统一方式挂在流程上。
- 出问题时可以更快分清楚是 parser、extract、vector、snapshot、graph 里的哪一段出问题。

所以它不是为了把代码写得“更学院派”，而是为了让链路从“能跑”升级成“可解释、可监控、可演进”。

代码证据：`WorkflowExecutionContext`、`IngestWorkflowService`、`QaWorkflowService`

### 原来那种顺序调用写法，最大的工程问题是什么

如果只能挑一个最大的工程问题，我会选“缺少结构化的流程边界”。因为没有显式流程边界，很多能力就会变得很难补：

- 很难统一返回“当前流程状态”，只能返回成功或失败。
- 很难区分“硬失败”和“可降级继续”。
- 很难统计每个阶段的重试和耗时。
- 很难判断某次失败是不是非法跳转、状态污染还是外部依赖抖动。
- 很难在未来插入新步骤，比如 query rewrite、rerank、工作流恢复。

换句话说，顺序调用不是错，而是它的工程上限比较低。它更适合函数内局部编排，不适合拿来承载需要状态表达、可观测性和扩展点的业务主链路。

### 现在这套状态机和“if/else + 枚举打标记”的本质区别

如果只是枚举打标记，通常只是“我现在把状态设成某个值”，但不会真正约束状态之间的关系。当前实现和简单枚举的本质区别，在于它把“状态”变成了一个可执行约束：

- 有明确的 `allowedTransitions`，不是任何状态都能随便跳。
- `transitionTo` 会校验当前迁移是否合法，非法就直接抛异常。
- `fail`、`finish`、`markDegraded`、`recordAttempt` 都挂在统一上下文里。
- 同一套执行上下文可以同时承载当前状态、降级原因、重试次数、开始/结束时间。

所以我会反驳“这不就是 if/else 加枚举吗”这个说法：`if/else + 枚举` 可以描述流程，但不能天然形成流程契约；而我现在这套轻量状态机，真正的价值是把流程契约做成了代码级约束。

当然我也不会把它吹成完整工作流平台。它仍然是单进程、轻量、无持久化工作流实例的状态机，不是 Spring StateMachine 这种更重的框架级方案。

代码证据：`src/main/java/com/agenthub/workflow/WorkflowExecutionContext.java`

### 入库工作流状态为什么设计成这几个，顺序为什么这样定

入库链路当前状态是：

- `RECEIVED`
- `PARSED`
- `CHUNKED`
- `EXTRACTED`
- `VECTOR_STORED`
- `SNAPSHOT_STORED`
- `GRAPH_STORED`
- `COMPLETED`
- `FAILED`

这组状态不是按“写了几个函数”来拆的，而是按“几个稳定里程碑”来拆的。

`RECEIVED` 表示流程已经被系统接受；`PARSED` 表示原始文档已经成功解析为可处理文本；`CHUNKED` 表示内容已经进入 chunk 级稳定形态；`EXTRACTED` 表示结构化知识已经从 chunk 中抽出来；`VECTOR_STORED` 表示核心检索面已经可用；`SNAPSHOT_STORED` 表示后续增量 diff 和恢复要用的快照已经存好；`GRAPH_STORED` 表示图谱这个派生视图也落好了；最后 `COMPLETED` 才代表整个流程对外可宣告结束。

这个顺序的核心逻辑是“先完成核心主链路，再补充运维和派生视图”。尤其要注意两点：

- `vector-store` 和 `snapshot-store` 在实现上是并发启动的，但对外暴露的状态顺序仍然先 `VECTOR_STORED` 再 `SNAPSHOT_STORED`。这不是线程顺序，而是业务优先级顺序。
- `vectorStore` 是硬依赖，写失败就整体失败；`snapshotStore` 和 `knowledgeGraph` 是软依赖，失败时记录降级后继续完成。

这能很好回答“为什么这个顺序这样定”：它不是只反映执行顺序，更反映业务承诺顺序。

代码证据：`IngestWorkflowService.ingest`、`IngestWorkflowService.allowedTransitions`

### 为什么单独拆出 `SNAPSHOT_STORED`，而不是并进 `VECTOR_STORED`

因为 snapshot 和 vector 虽然都属于“落库”，但角色完全不同。

`vectorStore` 对应的是在线检索主链路，决定文档能不能被语义检索命中；`snapshotStore` 对应的是增量更新和恢复基线，主要用于后续 `modified` 事件做 diff、重建和排障。它们的职责不同，失败语义也不同：

- `vectorStore` 失败意味着核心检索面不可用，所以当前设计里会直接失败。
- `snapshotStore` 失败不影响当前文档被查到，但会影响后续局部更新效率和恢复能力，所以当前设计里允许降级继续。

如果把 `SNAPSHOT_STORED` 并进 `VECTOR_STORED`，最直接的问题就是你会失去一个非常关键的观察面：当前数据是否已经“可检索但不可做稳定增量更新”。这在排障和监控里是非常有价值的。

再进一步说，当前 `KnowledgeUpdateAgent.handleModify` 会优先从 snapshot 读取旧 chunk，读不到才回退到 vector store。这说明 snapshot 不是“多存一份”，而是后续更新链路的重要基线。

代码证据：`DocumentSnapshotStore`、`RedisDocumentSnapshotStore`、`KnowledgeUpdateAgent.loadSnapshotOrFallback`

### 如果中间某一步少了，会对排障和监控造成什么问题

中间状态少了，最直接的问题不是“看起来没那么细”，而是你会失去故障归因能力。

几个典型例子：

- 没有 `EXTRACTED`，就分不清是抽取失败还是图谱写入失败。
- 没有 `VECTOR_STORED`，就无法判断文档是否已经进入主检索面。
- 没有 `SNAPSHOT_STORED`，就很难定位后续 diff 不准、局部更新失真到底是 snapshot 缺失还是 vector fallback 退化。
- 没有 `GRAPH_STORED`，图谱降级会被“总体完成”掩盖，业务方只会看到“入库成功”，却不知道图谱能力实际上不完整。

对于监控来说，中间状态本质上是漏斗节点。少一个状态，就少一层漏斗，也少一层告警分流依据。最后所有问题都会塌缩成“入库失败”或者“入库成功但效果一般”，排障成本会明显升高。

### 为什么问答工作流要单独建一套状态，而不是和入库共用一套抽象流程

我没有把 QA 直接塞进入库状态机里，是因为两个流程虽然共享“状态迁移”这个抽象，但它们的业务语义完全不同。

入库流程关注的是文档从原始输入到多路存储落地的过程；问答流程关注的是请求接收、记忆加载、检索融合、答案生成和回写的过程。两者共用一套大状态，最后只会得到一组很抽象、但业务解释力很弱的状态，比如“PROCESSING / STORED / COMPLETED”，这并不利于调试和表达。

所以我的做法是：共用轻量基础设施，不共用业务状态语义。基础设施层共用 `WorkflowExecutionContext` 和 `WorkflowStepRunner`，业务层各自定义自己的状态枚举，这样既避免重复造轮子，又保留流程语义的准确性。

### `QUESTION_RECEIVED -> MEMORY_LOADED -> RETRIEVAL_COMPLETED -> ANSWER_GENERATED -> COMPLETED` 各自代表什么

- `QUESTION_RECEIVED`：请求已经被接收并通过基本校验。
- `MEMORY_LOADED`：短期记忆阶段已经结束，不管是正常加载、没有历史，还是 memory 不可用后降级为空上下文，这一段都算完成。
- `RETRIEVAL_COMPLETED`：检索和混排都已经完成，问答链路已经拿到了可用于回答的上下文。
- `ANSWER_GENERATED`：模型回答已经生成完成，但流程还没彻底结束。
- `COMPLETED`：包括必要的 memory 回写等后处理都完成了，整个 workflow 正式结束。

这里最容易被追问的是为什么 `RETRIEVAL_COMPLETED` 和 `ANSWER_GENERATED` 要分开。我的回答是：检索质量和生成质量是两类不同问题。分开之后，能更清楚地区分“没检到东西”和“检到了但模型答得不好”。这对调试、评估和未来插入新步骤都非常关键。

### 如果以后做 query rewrite 或 rerank，应该插在哪个状态前后

当前 `RETRIEVAL_COMPLETED` 的语义比较宽，已经把“检索 + 混排”包进去了。如果以后要加 query rewrite，我会优先插在 `MEMORY_LOADED` 之后、真正检索之前，可能新增一个 `QUERY_REWRITTEN`。如果以后 rerank 复杂度变高，需要单独监控和评估，我会把现在的 `RETRIEVAL_COMPLETED` 再细拆成 `RETRIEVED` 和 `RERANK_COMPLETED`。

也就是说，当前状态机不是为了“一次性设计到最全”，而是为了给未来加阶段时保留一个干净的扩展点。

代码证据：`QaWorkflowService.allowedTransitions`

### 为什么没有用 Spring StateMachine，而是自己实现轻量状态机

这个项目当前的状态复杂度还没有大到必须上 Spring StateMachine。流程数量有限、状态数不多、没有长期挂起的工作流实例，也没有复杂事件驱动、并行 region、超时补偿和持久化恢复机制。在这个阶段，如果直接上 Spring StateMachine，收益有，但成本也很真实：

- 学习和配置成本更高。
- 框架引入后，排障复杂度和维护门槛会上升。
- 对当前这样的小型、同步主导、单进程工作流来说，容易出现“框架重量大于业务复杂度”的问题。

所以我现在选的是“自己实现一个足够小但有明确边界的状态机骨架”，把最核心的价值先拿到：合法迁移、统一上下文、降级与重试协同。

如果项目规模再扩大，我会考虑切到正式状态机框架的信号主要有这些：

- 工作流开始变成长时任务，需要持久化恢复。
- 状态数和迁移数明显膨胀，靠手写 `allowedTransitions` 开始难维护。
- 需要多 actor 协调、事件驱动转换、超时事件、并发分支。
- 需要更强的可视化、声明式定义和框架级扩展能力。

当前这套实现最大的短板也恰恰在这里：它轻量、清楚，但不具备持久化工作流实例、恢复编排、复杂并发状态和图形化管理能力。

### 为什么把重试逻辑抽到统一的 `WorkflowStepRunner`

把重试逻辑统一抽出来，当然有复用性，但真正更重要的是它统一了“每一步怎么重试、怎么记次数、怎么向上暴露”。这解决的不只是少写几遍 `for` 循环，而是工程一致性问题：

- 所有 workflow 的重试语义一致。
- `retryAttempts` 的统计口径一致。
- 每个阶段的名字一致，便于监控和排障。
- 降级逻辑可以围绕统一的 step 名称和失败点展开。

`retryAttempts` 当前返回的是“额外重试次数”，而不是“总尝试次数”。这是一个很有意识的设计：因为业务方更关心“有没有额外重试过”，而不是“第一次执行也算一次尝试”。如果某一步一次成功，返回 `0` 比返回 `1` 更符合直觉。

当然，统一重试有一个前提：被重试的步骤本身要么幂等，要么重复执行的副作用可接受。如果某一步不是幂等的，统一重试就会带来重复写入、重复调用外部接口或部分状态污染的风险。这种场景下要么关闭统一重试，要么给该步骤补幂等键、upsert 语义、事务保护或补偿逻辑。

代码证据：`WorkflowStepRunner`、`WorkflowExecutionContext.retryAttempts`

### 哪些阶段允许降级，哪些阶段不允许，原则是什么

我当前的划分原则，不是单纯“核心链路优先”或者“用户可感知优先”二选一，而是更具体的一条：**只要某个阶段失败后，系统仍然能安全地提供一个语义明确、不会误导上层的结果，就允许降级；反之就必须失败。**

按这个原则看：

- 入库流程里，`vectorStore` 不允许降级，因为它是主检索面，没有它这次入库就不算真正可用。
- `snapshotStore` 允许降级，因为它影响的是后续 diff、恢复和运维，不影响当前文档立即进入主检索面。
- `knowledgeGraph` 允许降级，因为图谱是派生视图，不是当前最小可用能力的唯一来源。
- `docParser` 和 workflow 级 `knowledgeExtract` 不允许降级，因为一旦它们整个阶段失败，后面就没有可信的输入继续执行。

这里要补一个实现细节：从 workflow 视角看，`knowledgeExtract` 属于硬依赖；但在 agent 内部，单个 chunk 的抽取返回如果无法解析成 JSON，`parseResponse` 会回退为空实体/关系，而不是直接炸掉整个 workflow。这是 agent 内部的细粒度容错，不等同于 workflow 级降级。

QA 流程里的逻辑类似，但更偏“用户可感知最小可用回答”：

- `memory` 不可用时允许降级为空记忆上下文。
- `vector` 挂了但 `graph` 还有结果，可以继续回答。
- `graph` 挂了但 `vector` 还有结果，也可以继续回答。
- 只有当单路失败后另一条路也没有可用结果时，当前实现才直接失败。

需要坦诚的一点是：如果两条路都没报错但都没召回到上下文，当前实现不会强制失败，而是允许模型在空上下文下保守回答。这说明 QA 降级策略已经有骨架，但还不是非常严格的“有证据才答”体系。

### 如果出现非法状态迁移，现在怎么处理，为什么不能偷偷纠正

当前策略是直接抛 `IllegalStateException`。我不会偷偷把非法状态纠正成合法状态，因为非法迁移通常不是什么“小毛刺”，而是在提醒我们有更底层的问题：

- 代码路径有 bug。
- 并发顺序出了问题。
- 恢复逻辑和当前状态定义不一致。
- 状态已经被污染，或者外部依赖结果和预期不一致。

如果这时候偷偷纠正，表面上是“系统更健壮了”，但实际上是在掩盖 bug。工程上更合理的做法是尽快暴露这个问题，把非法迁移视为契约被破坏，而不是视为一个可以自动修正的小错误。

如果以后要做工作流恢复，我会保留非法迁移校验，但会把它和恢复机制结合起来：恢复前先校验持久化状态是否合法、恢复点是否可继续、是否需要进入专门的恢复分支，而不是直接把非法状态吞掉。

至于并发场景，当前实现里的 `transitionTo`、`fail`、`finish` 都用了 `synchronized`，对于当前这种“少量异步分支最后统一 join，再由主流程推进状态”的单进程模式是够用的；但它还不适合多个 actor 同时竞争推进同一个 workflow，也不具备分布式并发控制能力。这也是当前轻量实现的边界之一。

## 2. Kafka 增量更新

### Kafka 增量更新链路的主流程是什么

这条链路从 `@KafkaListener` 收到消息开始，整体可以概括成“解析事件 -> 幂等与顺序保护 -> 事件状态落盘 -> 分发变更处理 -> 更新完成后写回状态”。更完整一点说：

1. Kafka 收到 CDC 消息，进入 `KnowledgeUpdateAgent.handleCDCEvent`。
2. 解析原始 JSON，构造成 `DocumentChangeEvent`。
3. 在真正处理前先做 `shouldSkipEvent`，挡住重复事件、旧版本事件和旧时间戳事件。
4. 对通过检查的事件，先写 `RECEIVED`，再写 `PROCESSING` 到 `EventProcessingStore`。
5. 根据 `changeType` 分发到 `handleCreate`、`handleModify` 或 `handleDelete`。
6. 执行对应的向量、图谱、快照更新逻辑。
7. 成功后更新进程内版本/时间戳缓存，并把事件记为 `SUCCEEDED`，同时持久化最后成功处理的版本和时间戳。
8. 失败时统一写 `FAILED`，再由 Spring Kafka 错误处理器决定重试、DLT 或直接终止。

这个主流程的重要意义在于：它已经不只是“消费一条消息做一次更新”，而是围绕幂等、顺序、可恢复和可排障做了工程骨架。

代码证据：`KnowledgeUpdateAgent`、`EventProcessingStore`、`KafkaConsumerConfig`

### 哪一步负责幂等，哪一步负责顺序保护，哪一步负责局部更新

这三个能力在实现里分工比较清楚：

- 幂等主要由 `shouldSkipEvent` 负责，靠 `eventId` 去重、已成功事件跳过、进程内 `processedEventIds` 快速挡重。
- 顺序保护也主要由 `shouldSkipEvent` 负责，但依赖的是 `version` 和 `timestamp` 两层判断。
- 局部更新由 `handleModify` 负责，它基于 snapshot 和当前解析结果做 `ChunkDiff`，只处理受影响的 chunk。

也就是说，幂等和顺序保护是在“是否进入处理链路”这一层解决的；局部更新是在“进入处理链路之后，怎么尽量少改数据”这一层解决的。

### 如果让我口述一遍 `modified` 事件处理链路，我会怎么讲

比较适合面试里的口述版本是：

“`modified` 事件进来以后，我先把消息解析成结构化事件，然后先做幂等和顺序保护。幂等主要看 `eventId` 和已成功处理记录，顺序保护优先看 `version`，没有版本号再回退到 `timestamp`。只有通过这两层检查，事件才会进入正式处理。”

“正式处理时，我先根据文件路径算 `docId`，优先从 snapshot 里拿旧 chunk；如果 snapshot 没有，再从 vector store 回退加载旧 chunk。接着重新 parse 当前文档，拿新旧两版 chunk 做 diff，得到三类结果：没变的、变了的、删掉的。”

“然后我会把 `changed chunk` 和 `removed chunk` 一起并入 `staleChunkIds`，先并发删除旧向量和旧图谱关系，再把变更后的 chunk 重新写入向量库，并重新抽取知识 upsert 到图谱里。最后把最新 chunk 列表写回 snapshot。如果文档改完已经没有 chunk 了，就删掉 snapshot。”

“处理成功以后，再把事件状态记成 `SUCCEEDED`，并把最后成功版本和时间戳写回持久化存储，供后续幂等和顺序保护继续使用。失败则写 `FAILED`，交给 Kafka 重试和 DLT 机制处理。”

这段口述能比较自然地把幂等、顺序、局部更新和多存储更新串起来。

### 为什么我认为这条链路已经不是 demo 级消费了

我不会说它已经是完整生产级闭环，但我会明确说：它已经明显超过 demo 级消费。因为它不只是“收到消息后调用一个 handler”，而是具备了生产链路最关键的一批工程能力：

- 有结构化事件模型，而不是随手 parse 一下 JSON 就处理。
- 有幂等和顺序保护，而不是默认相信 Kafka 不重复、不乱序。
- `modified` 支持 chunk diff 局部更新，而不是全量删重建。
- 有事件状态持久化，能区分 `RECEIVED / PROCESSING / SUCCEEDED / FAILED`。
- 有失败重试、DLT 和 replay，而不是失败直接丢日志。
- 有快照、版本、时间戳和 payload 存储，便于排障和恢复。
- 有单测固化关键行为，不是只跑通 happy path。

如果非要挑一个还没完全生产级的地方，我会说它还不是跨 Kafka、Milvus、Neo4j、Redis 的事务闭环，也不是完整补偿平台。但有这些边界，不等于它还是 demo。

### 为什么顺序保护里同时保留 `eventId`、`version` 和 `timestamp` 三层判断

因为这三层解决的不是同一个问题。

`eventId` 解决的是“这是不是同一条事件又来了一次”。它适合挡重复投递，但挡不住“旧事件晚到但 `eventId` 不同”的场景。所以单靠 `eventId` 不够。

`version` 解决的是“这条事件在业务顺序上是新还是旧”。这比 `timestamp` 更接近真实业务语义，因为它来自变更序列本身。对乱序覆盖问题，`version` 是最稳的一层。

`timestamp` 是最后的兜底。它主要在 `version` 缺失时发挥作用，至少能让系统具备一个“弱顺序保护”，避免明显旧的事件覆盖新的状态。

所以三层判断不是重复建设，而是：

- `eventId` 管重复。
- `version` 管业务顺序。
- `timestamp` 管缺版本号时的弱顺序兜底。

### 单靠 `eventId` 不够，单靠 `timestamp` 也不够，回退到 `timestamp` 有什么风险

单靠 `eventId` 不够，是因为两个不同事件完全可能作用于同一个文件，而且先后顺序很重要。旧版本事件晚到时，`eventId` 看不出来它旧不旧，只知道“它不是重复事件”。

单靠 `timestamp` 也不够，因为时间戳有天然边界：

- 上游系统可能有时钟偏差。
- 多条事件可能时间戳很接近，甚至一样。
- 时间戳只能近似反映发生先后，不一定严格代表业务版本先后。

所以当前实现是“优先 `version`，缺失时退回 `timestamp`”。这个回退是有价值的，但我会明确承认它的边界：它是 best-effort 顺序保护，不是强一致排序保证。如果以后接入真正稳定的 CDC 版本号，我会把 `version` 变成主判据，把 `timestamp` 彻底降成辅助参考或排障信息。

### 现在的幂等到底做到什么程度

我会把当前幂等描述成“内存级 + 持久化级保护已经有了，但还不是跨系统完全闭环的 exactly-once”。

内存级主要体现在 `processedEventIds`、`documentVersions`、`lastProcessedTimestamps` 这些进程内结构上，它们的价值是热路径快、开销低、可以减少对 Redis 的依赖频率。缺点也很明确：服务重启后这些保护会丢失。

持久化级主要体现在 `EventProcessingStore`，它补上的能力包括：

- 已成功事件跨重启去重。
- 最后成功版本和时间戳持久化。
- 失败原因持久化。
- 原始 payload 持久化，为 replay 提供依据。
- 事件状态查询能力。

所以服务重启后，内存去重会失效，但持久化级的幂等和顺序保护还在。这就是为什么我会说当前已经不是纯内存 demo 了。

但我也不会说它已经完全闭环。因为 Kafka 消费、Redis 状态写入、Milvus 更新、Neo4j 更新之间还没有一个统一的跨系统原子事务，所以它不是严格意义上的 exactly-once。

代码证据：`KnowledgeUpdateAgent.shouldSkipEvent`、`RedisEventProcessingStore`

### 为什么 `modified` 更新做成 chunk diff，而不是整篇删除后全量重建

因为在这个项目里，全量重建的代价其实很高，而且不必要。

文档修改后，如果只改了一个 chunk，但你删整篇再重建，会带来这些额外开销：

- 不必要的 embedding 计算。
- 不必要的 LLM 抽取调用。
- 不必要的向量写入和图谱重建。
- 更大的处理时延。
- 更大的外部依赖压力。

当前 diff 的判定逻辑是：先按 `chunkId` 对齐旧 chunk 和新 chunk，再用 `contentHash()` 判断相同 `chunkId` 下内容是否真的变化。也就是说，`chunkId` 决定“是不是同一个位置的 chunk”，`contentHash` 决定“这个 chunk 内容有没有变”。

这里也有一个我会主动讲清楚的边界：当前 `chunkId` 基于 `docId + chunkIndex`，如果 chunk 切分策略发生明显变化，或者前面插入内容导致后续 chunk 边界整体漂移，那么 diff 很可能退化成大面积重建。它不会直接造成正确性错误，但会削弱局部更新的效率。如果后续 chunk 策略变得更动态，就需要考虑更稳的 fingerprint 或 anchor-based diff。

代码证据：`DocumentChunk.contentHash`、`KnowledgeUpdateAgent.ChunkDiff`、`DocParserAgent.chunkText`

### 文档修改后，怎么保证旧向量和旧图谱边不会残留

核心做法是先删旧，再写新，而且删的范围不是只看 removed chunk，而是看 `staleChunkIds`。当前实现里，`staleChunkIds` 包含两类：

- `removed chunk`
- `changed chunk`

为什么 changed chunk 也要进 `staleChunkIds`？因为 changed chunk 虽然逻辑上还是“同一个位置”，但旧内容对应的向量和旧关系已经失效了。如果不先清理，直接写新数据，就可能在向量库和图谱里留下旧内容痕迹。

为什么要先删再写？因为如果先写后删，最危险的情况是：

- 新旧向量短暂并存，召回结果混杂。
- 图谱里新旧边同时存在，关系污染。
- 删除逻辑如果按 chunk 粒度不够精确，甚至可能把刚写入的新数据误删掉。

所以当前顺序是先把 stale 数据清干净，再写 changed chunk，这样更容易保证结果至少朝着“单向收敛”前进。

### 为什么把 vector delete 和 graph delete 做成并发，而不是顺序执行

这两个动作天然适合并发，因为它们写的是两个独立存储：一个是向量库，一个是图数据库。两边没有同步依赖关系，也不共享同一事务上下文，所以串行执行的唯一结果就是拉长时延。

但并发并不等于没有一致性问题。如果其中一个成功、另一个失败，当前仍然可能留下跨存储不一致。例如：

- 向量删掉了，但图谱还保留旧边。
- 图谱删掉了，但向量里还保留旧 chunk。

我现在没有做事务级一致性保证，所以我不会把这条链路包装成强一致。更准确的说法是：当前是一条尽量缩短窗口、但仍然接受短时跨存储不一致风险的工程链路。如果未来要更进一步，可以往补偿重试、异步 reconcile、对账修复或 saga/outbox 方向演进。

### Kafka 失败处理算不算完全闭环

我会回答：**已经有失败闭环骨架，但还不是完整补偿平台。**

当前链路里：

- 非可重试异常会写 `FAILED`，并被 Spring Kafka 标记成不重试。
- 可重试异常会写 `FAILED`，然后由 `DefaultErrorHandler` 做固定退避重试。
- 超过重试次数后会进入 DLT。
- 事件状态和原始 payload 都能查询。
- 失败事件支持 replay。

这已经比“失败打日志”强很多了。但为什么我还不说它是完整补偿平台？因为它还缺少这些能力：

- 没有批量 replay、批量筛查和自动修复流程。
- 没有跨存储对账能力。
- 没有“哪个阶段失败、该怎么定向补偿”的平台化编排。
- 没有保证 replay 一定只触发最小副作用。

所以它是“具备补偿入口”，但不是“完整补偿系统”。

### 如果面试官问“消息能不能保证绝对不丢不重”，怎么界定边界

我会非常明确地说：当前实现不承诺跨 Kafka、Redis、Milvus、Neo4j 的“绝对不丢不重”或严格 exactly-once。我现在做到的是：

- 尽量减少重复处理带来的业务副作用。
- 在服务重启后保留主要的幂等和顺序保护。
- 在失败后保留重试、DLT 和 replay 能力。

这已经是工程化闭环的一大步，但不是分布式事务级保证。面试里稳妥的说法不是“绝对不丢不重”，而是“我把问题拆成去重、顺序保护、失败恢复和一致性边界分别处理，并且明确知道还没做到事务级 exactly-once”。

### 如果连续两次修改同一个文档，旧事件晚到，怎么避免旧状态覆盖新状态

这件事当前主要靠 `version` 兜住，`timestamp` 是缺版本号时的后备。只要更新事件带了稳定版本号，旧版本晚到就会在进入处理前被 `shouldSkipEvent` 拦掉。

`deleted` 和 `modified` 的顺序判断逻辑之所以不完全一样，是因为删除事件在工程上更适合保留同版本 replay 的空间。当前代码里，`deleted` 用的是 `<` 判断陈旧，其他更新用的是 `<=`。这样做的含义是：同版本的 delete replay 仍然允许继续作为幂等删除执行，而不是被一刀切挡掉。

如果未来接入真正的 CDC 版本号，我会进一步收紧这套逻辑：

- 把版本号作为绝对主判据。
- 把时间戳退化成辅助诊断信息。
- 视上游 CDC 语义决定 delete 和 modify 是否需要进一步区分 replay 策略。

## 3. QA 与混合检索

### 为什么选择“向量检索 + 图谱检索”双路融合，而不是只做一个 RAG

因为这两条路解决的问题不一样。

向量检索擅长找“语义接近的文本片段”，特别适合描述型问题、流程型问题、定义解释类问题；图谱检索擅长找“结构化关系”，特别适合实体关系、依赖链、归属关系这类问题。只做一个纯向量 RAG，当然能覆盖大量场景，但在“关系是否存在、链路怎么连”这类问题上，图谱提供的证据形态会更直接、更可解释。

图谱在这个项目里最大的价值，不是替代向量，而是给出一条结构化证据通路。哪怕当前图谱召回质量还不是特别强，它仍然值得保留，因为它至少带来了三件额外的东西：

- 关系型问题上的补充召回。
- 更可解释的结构化上下文。
- 在 vector 和 graph 结果不一致时，帮助系统识别冲突，而不是默认一切都一致。

所以双路融合不是“为了显得复杂”，而是承认不同问题需要不同证据形态。

### 怎么区分关系型问题和描述型问题，为什么先用轻量规则

当前是用轻量关键词规则做分类。包含“关系、关联、属于、依赖、relationship、depends on”等关键词时，会判为 `RELATIONSHIP`；否则默认 `DESCRIPTIVE`。

我先用规则而不是上 LLM 分类，主要是因为这个阶段更需要低成本、可解释、可控的 baseline。规则方案最大的优点是：

- 成本低。
- 可解释。
- 不引入额外模型调用延迟和不稳定性。
- 方便快速迭代。

它最大的缺点也很明确：覆盖有限，容易误分类。好在当前实现里双路检索本身都会执行，分类主要影响的是混排权重和上下文排序，而不是某一路会被完全关掉。所以误分类首先影响的是 rerank 和最终回答质量，而不是直接把召回路由打没。

如果以后升级，我最优先会加的是更稳的 query intent 识别，但不会一上来就做复杂 LLM classifier。原因很简单：当前权重体系本身还是启发式 baseline，在这之前先把评测和数据闭环补起来，收益通常比先堆更复杂的分类模型更大。

代码证据：`QAAgent.detectQuestionMode`

### 双路混排的权重是怎么定的，为什么关系型 graph 权重大、描述型 vector 权重大

当前混排本质上是按问题类型切换的线性重打分：

- 关系型问题：`vector * 0.80`，`graph * 1.40`
- 描述型问题：`vector * 1.20`，`graph * 0.90`

此外还有两个小补偿：

- 关系题如果 graph 证据太少，会给 vector 一个轻微回补。
- 描述题如果没有高置信 graph 结果，会再轻微压低 graph 分数。

为什么这样定？因为关系型问题更看重结构化关系证据，graph 在这种问题上更“贴题”；描述型问题更依赖段落级上下文，vector 更“贴题”。所以这里的权重不是在比“谁更强”，而是在比“当前问题下谁的证据形态更匹配”。

我会把这套权重定义成**启发式 baseline**，不是实验最优，也不是拍脑袋乱写。它的来源更接近“基于问题形态差异做的经验设定，再用单测把方向性固化”。当前仓库里没有离线标注评测、没有 learning-to-rank 训练数据，所以我不会夸它是精调出来的最优值。

如果面试官追问“怎么证明它至少合理”，我会从三个层面回答：

- 它是偏置，不是硬切路。两条路都还保留，不会因为分类误差把一整条证据链砍掉。
- 单测明确验证了关系题 graph 排前、描述题 vector 排前这个方向性目标。
- 它是当前证据尺度还没完全校准前，一种可解释、低成本、可迭代的 baseline。

我还会主动承认一个局限：当前 graph 结果分数本身比较粗，甚至固定在 0.8 附近，这说明现在的混排更多是启发式校准，而不是已经做过严格分数归一和排序学习的系统。

代码证据：`QAAgent.hybridRerank`、`QAAgentTest`

### 如果面试官问“为什么不是学习排序”，我会怎么回答

我会说，现在先不用学习排序，不是因为它不好，而是因为前提还没齐：

- 当前没有标注数据、点击反馈或人工偏好数据。
- 两条路的原始分数尺度还没真正对齐。
- 当前更需要一个可解释、可调、易排障的 baseline。

在这种前提下直接上 learning-to-rank，风险是模型复杂度上去了，但你未必真的学到稳定东西。更合理的路线是：先把启发式 baseline、日志、评测集和特征记录补齐，再考虑 LambdaMART 或更轻量的 ranker。这样顺序更稳。

### 单路失败时，为什么选择降级继续回答，而不是直接失败

因为当前问答系统不是单一证据源系统。只要还有一条路能提供足够上下文，直接失败通常会比降级继续更差。

所以我当前的判断是：

- `vector` 挂了但 `graph` 还有结果，可以继续答，尤其是关系型问题。
- `graph` 挂了但 `vector` 还有结果，也可以继续答，尤其是描述型问题。
- 只有当一条路失败后，另一条路也没有结果时，当前实现才直接失败。

这背后的原则是“只要还能给出一个语义明确、证据来源可解释的回答，就优先降级继续”。不过这里也要坦诚边界：当前实现对“空召回但不报错”的情况还不够严格，它不会一律失败，而是允许模型在弱上下文甚至空上下文下保守回答。这说明 QA 降级体系已经成型，但还没有进化成严格的回答门禁系统。

### 为什么要给 `QAResult` 增加 `degraded`、`degradeReasons`、`workflowState`

如果只有 `reasoningSteps`，很多信息都还是“给人看懂可以，但给系统消费不方便”。`QAResult` 增加这几个结构化字段，本质上是在把“调试线索”变成“上层策略可以直接读的字段”。

- `degraded`：这次回答是不是降级产物。
- `degradeReasons`：到底是哪条能力不可用。
- `workflowState`：问答 workflow 走到了什么状态。

以前只靠 `reasoningSteps` 的问题是：它更像日志，不像契约。前端或上层系统如果要根据问答质量做策略，比如标注弱回答、触发重试、提示用户结果可信度下降，就很难只靠非结构化文本做稳定判断。

接口层和调试日志的边界也在这里：接口层应该给结构化状态，日志层可以继续保留详细推理文本。两者不是互相替代，而是职责不同。

代码证据：`QAResult`、`QaWorkflowService.mergeWorkflowMetadata`

### 为什么把上下文拆成 `[MEMORY]`、`[VECTOR_CONTEXTS]`、`[GRAPH_CONTEXTS]`、`[CONFLICT_HINTS]`

因为如果把这些内容全都混成一坨文本交给模型，模型很难理解“哪些是历史对话、哪些是语义片段、哪些是图谱关系、哪些是冲突提醒”。拆开之后的价值有三个：

- 证据类型边界更清楚，模型更容易按用途消费。
- 出现问题时更容易判断是 memory 污染、vector 召回偏了还是 graph 冲突。
- 这本身就是一种轻量可解释性设计，上层系统和开发者都更容易理解回答依据。

`CONFLICT_HINTS` 解决的不是所有冲突治理，而是一个很具体的问题：当 vector 和 graph 指向不同主来源时，不要默认它们是一致的，要显式提醒模型更保守、尽量引用证据。这能减少模型在冲突上下文里无脑综合的风险。

### 怎么识别 vector 和 graph 的来源冲突，现在真正做了什么、还没做什么

当前来源冲突识别非常轻量：拿 vector 第一条结果和 graph 第一条结果的 `source` 做比较，如果不一致，就标记 `SOURCE_CONFLICT`。

识别出来之后，我现在真正做的事情有两件：

- 在 `reasoningSteps` 里显式打出 `SOURCE_CONFLICT`。
- 在 prompt 里加入 `[CONFLICT_HINTS]`，要求模型更保守地回答。

我现在没做的事情同样要讲清楚：

- 没有自动判定谁更可信。
- 没有冲突仲裁策略。
- 没有冲突级别分层。
- 没有基于冲突触发拒答或进一步检索。

所以这不算完整冲突治理，更准确地说，它是“冲突识别 + 提示性防御”的第一步。

## 4. 图谱与数据一致性

### 为什么实体身份设计成稳定键，而不是简单按名字 merge

如果只按 `name` 合并实体，最容易出现的问题就是跨来源污染。不同文档里的同名实体不一定是同一个真实对象，如果只按名字 merge，图谱会快速变脏：关系串错、来源串错、上下文串错。

当前设计里的稳定键，本质上是 `source + entityName` 的组合规范化结果。它解决的是“同名不同来源不要轻易合并”的问题。这个策略的优点是保守、稳，优先避免脏合并；缺点也要坦诚：它并没有真正做跨来源实体对齐，所以会带来一定召回碎片化。

我会把这件事解释成一个有意识的 trade-off：当前阶段我优先保证图谱不被错误 merge 污染，而不是过早做激进实体融合。等后续数据规模和对齐需求上来，再补实体消歧和跨源对齐。

代码证据：`KnowledgeGraphService.buildEntityKey`、`KnowledgeGraphServiceTest`

### 为什么补 `deleteBySourceAndChunkIds`，而不是继续只保留 `deleteBySource`

因为一旦你要做 chunk 级局部更新，整文档删除就不够用了。

如果只有 `deleteBySource`，那每次有一个 chunk 变了，你只能整篇文档的图谱数据全删再重建。这样做的问题有两个：

- 效率差，局部更新退化成全量重建。
- 正确性差，如果并发更新或失败恢复没处理好，容易出现新旧数据交织。

`deleteBySourceAndChunkIds` 和 chunk diff 是配套能力：chunk diff 告诉系统“哪些 chunk 脏了”，图谱删除能力则确保系统能精确清掉这些 chunk 关联的旧关系和旧实体引用。

### 为什么把图谱“不可用”从静默空结果改成显式抛异常

因为“图谱不可用”和“图谱里真的没有结果”是两种完全不同的语义。

如果图谱挂了却静默返回空列表，上层 workflow 会误以为“这次只是没搜到”，从而把故障误判成正常空召回。这样一来：

- 降级体系无法成立，因为上层根本不知道图谱坏了。
- 监控会把故障吞掉。
- QA 结果会看起来像是正常检索结果，只是质量差。

只有显式抛异常，上层 workflow 才能正确把它识别成 `GRAPH_UNAVAILABLE`，再决定是降级继续还是整体失败。所以这个改动本质上是降级体系成立的前提条件之一。

### 文档修改后，怎么避免旧边和旧实体残留

当前图谱删除的设计依赖了两类元数据：

- 关系上带 `source` 和 `chunk_id`
- 实体节点上带 `source` 和 `chunk_ids`

关系删除比较直接，按 `source + chunk_id` 清理对应边；实体删除则更细一些：先把命中的 `chunk_id` 从实体的 `chunk_ids` 列表里移除，只有当实体不再属于任何 chunk 时，才真正删除节点。这样能避免“一个实体仍被其他 chunk 引用，却被过早删掉”的问题。

这也是为什么实体节点上要带 chunk 维度信息。没有这个维度，你很难在局部更新场景里只删掉该删的部分。

如果后面做 chunk 合并、chunk 重排或更复杂的 chunk 演化，这套删除语义会变复杂，但复杂点恰恰不是图谱删除本身，而是“如何稳定映射 chunk 身份”。这还是会回到 diff 策略设计上。

### 为什么图谱检索还是“实体命中 + 邻居扩展”的轻量方案

因为当前阶段更适合先做一个轻量、可解释、成本可控的 graph-enhanced retrieval。

这套方案的优点很明确：

- 实现成本低。
- 易于解释，能说清楚为什么命中了哪些节点。
- 对当前图规模和项目阶段足够用。
- 和现有关键词抽取、关系存储方式比较匹配。

它的质量上限也很明确：

- 没有复杂路径打分。
- 没有更强的 query understanding。
- 没有全局图算法或图学习能力。
- 对图质量和实体命中质量比较敏感。

如果面试官说“这看起来不像真正的图算法检索”，我会正面承认：对，当前它不是重图算法方案，而是一种轻量图谱增强检索。它的目标不是炫技，而是在当前阶段用最小复杂度把结构化证据链接进问答系统。

## 5. Redis 记忆

### 为什么在 Java 版里保留 Redis 短期记忆，而不是只做无状态问答

因为这个项目里问答并不总是单轮独立问题。只做无状态问答，很多多轮追问、指代消解和上下文延续都很难处理。短期记忆主要解决的是这些问题：

- “这个改动里它为什么这样做”里的“它”指代谁。
- 用户上一轮刚问过 workflow，这一轮继续追问某个状态。
- 多轮问答需要保留近几轮对话语义。

我现在只做短期记忆，不急着做长期记忆，是因为短期记忆已经覆盖了当前最常见的对话场景，而且工程复杂度更可控。长期记忆会引入更大的检索、归档、过期和知识漂移问题，不适合在当前阶段一口气全上。

如果 session 很长，这套方案最先遇到的问题不是“存不下”，而是 prompt 预算和噪声累积。也正因为如此，我才会对窗口、总长度和单条消息长度做控制。

### 怎么区分“没有历史消息”和“memory 不可用”，为什么重要

当前不是简单返回一个字符串，而是通过 `LoadResult` 和 `MemoryLoadResult` 显式携带 `available` 标志。这样可以区分两种完全不同的情况：

- 没有历史消息：这是正常情况，不该算故障。
- memory 不可用：这是降级，应该被 workflow 标出来。

这个区分非常重要。因为如果两者最后都只是表现成空字符串，上层 workflow 就无法知道这次是不是发生了依赖故障，也就没法正确填 `degraded` 和 `degradeReasons`。对接口和监控来说，这两者是完全不同的语义。

`MemoryLoadResult` 相比直接返回 `String` 的提升，核心就在于它把“数据”和“可用性”拆开了。

代码证据：`ShortTermMemoryService.LoadResult`、`MemoryManager.MemoryLoadResult`、`QaWorkflowServiceTest.shouldMarkResultDegradedWhenMemoryUnavailable`

### 为什么要控制消息窗口、上下文总长度和单条消息最大长度

如果不做这些限制，最坏情况会出现三类问题：

- prompt 越堆越长，成本和延迟失控。
- 旧消息噪声淹没当前问题。
- 单条超长消息把上下文预算直接吃光。

当前参数大致可以这么解释：

- 保留 20 条：偏存储层，是短期历史缓存容量。
- 读取 10 条：偏推理层，是进入 prompt 的近窗口。
- 2000 字符预算：偏 prompt 预算，防止 memory 挤占太多上下文。
- 单条 300 字符裁剪：防止个别消息失控。

这些值我不会说成“效果最优参数”，更稳妥的表达是：它们是当前阶段的系统参数和安全默认值，目的是控制上下文预算、保住多轮连续性，并避免 memory 抢占主检索证据空间。

### 为什么强调“当前轮问题不能提前写入 memory 再拼 prompt”

因为如果当前轮问题先写进 memory，再把 memory 拼进 prompt，会造成当前问题重复出现：一次在用户输入里，一次在 memory 里。这样不仅浪费上下文预算，还会让 prompt 结构变得冗余，甚至影响模型对“历史 vs 当前问题”的判断。

当前问答 workflow 的顺序是：

1. 先加载 memory
2. 用加载出来的上下文回答当前问题
3. 回答完成后再把当前轮 user/assistant 消息写回 memory

这个顺序更符合真实对话语义：memory 只表示“在当前轮之前已经发生过的对话”，而不是把当前轮问题混进去。

代码证据：`QaWorkflowService.ask`、`QaWorkflowServiceTest.shouldLoadMemoryBeforePersistingCurrentTurn`

## 6. Virtual Threads

### 为什么在抽取、入库、更新这些地方优先接入 Virtual Threads

因为这几个点有一个共同特征：它们都是我们自己控制的、I/O 型或阻塞型子任务编排点，而且天然存在 fan-out 或并行阶段。

- `KnowledgeExtractAgent`：chunk 级抽取是典型的多任务并发。
- `IngestWorkflowService`：vector 和 snapshot 写入可以并发。
- `KnowledgeUpdateAgent`：vector delete 和 graph delete 可以并发。

这些地方比 Controller 层更适合先接入 Virtual Threads，因为它们的线程模型掌握在我们自己手里。先在业务子任务层引入，风险小、收益明确、也更容易验证。相反，如果一开始就动 Spring Web 或 Kafka 容器线程模型，改动面会更大，验证和回滚成本也更高。

### 为什么说“不是只用了 Java 21，而是真的用了 Virtual Threads”

如果只是把 JDK 升到 21，但业务任务还是跑在原来那套线程池上，那不能叫“真正用了 Virtual Threads”。当前实现之所以能比较有把握地说“用上了”，关键在于它有统一的 `workflowExecutor` 抽象：

- 执行模式通过 `app.execution.mode` 切换 `platform` 或 `virtual`
- `KnowledgeExtractAgent`、`IngestWorkflowService`、`KnowledgeUpdateAgent` 这些业务并发点都显式注入并使用同一个执行器
- benchmark 也是围绕这个执行器切换做的

如果没有执行器抽象，这件事会非常难验证，因为你很难证明业务子任务到底跑在哪个线程模型上。

代码证据：`ExecutionConfig`、`KnowledgeExtractAgent`、`IngestWorkflowService.runStageAsync`、`KnowledgeUpdateAgent`

### 为什么在 chunk 抽取这里还要加 `Semaphore`

因为“虚拟线程很轻”不等于“外部依赖能承受无限并发”。`KnowledgeExtractAgent` 的瓶颈不只是线程，而是外部 LLM 调用、网络、限流和整体系统压力。

所以这里真正的设计思想是“Virtual Threads + 并发上限”，而不是“Virtual Threads + 无限 fan-out”。虚拟线程解决的是本地阻塞任务编排成本，`Semaphore` 解决的是外部依赖保护和背压控制。两者解决的问题根本不是一回事。

### 为什么要保证并发抽取后结果顺序仍然和输入 chunk 顺序一致

这就是一个典型的并发正确性问题。并发执行之后，如果结果顺序漂了，后面很多依赖 `sourceChunkId`、chunk 顺序或稳定行为的逻辑都会变得更难推理和调试。

当前实现的做法其实很简单但有效：虽然每个 chunk 的抽取任务是并发提交的，但最后收集结果时，仍然按提交顺序遍历 `futures` 并依次 `join`，所以返回列表顺序和输入 chunk 顺序保持一致。

这种设计的好处是：既吃到了并发带来的吞吐提升，又保住了输出顺序的确定性。

代码证据：`KnowledgeExtractAgent.extract`

### benchmark 到底证明了什么，又不能证明什么

当前 benchmark 证明的是：在一个本地模拟的阻塞型任务场景下，使用虚拟线程执行大量 sleep-heavy 任务，会比固定少量平台线程更快完成。这说明“对于阻塞型并发任务，当前这套执行器抽象确实能把虚拟线程的调度优势用出来”。

但它不能直接证明真实业务吞吐一定提升了多少，更不能直接外推成线上 QPS 提升。原因很简单：真实业务里还有外部模型响应时间、Milvus、Neo4j、网络、限流、序列化和上下游依赖，这些都不是一个 `Thread.sleep` microbenchmark 能覆盖的。

如果面试官拿“24 个任务、每个 80ms 阻塞、平台线程约 480ms、虚拟线程接近 80ms”来问，我会这么讲：这组数字只能说明在理想化阻塞场景下，虚拟线程能接近“一批并发完成”的效果，而平台线程更接近“分批排队完成”。它是一个执行模型验证，不是业务吞吐承诺。

代码证据：`VirtualThreadWorkflowBenchmarkTest`

### 为什么现在还不能说“整个服务已经虚拟线程化”

因为当前被我显式切到 `workflowExecutor` 上的，只是自己控制的业务子任务。Spring Web 请求线程、Kafka listener 容器线程，以及某些底层客户端的线程模型，仍然主要由框架控制。

这也是为什么我只会说“业务子任务已经接入 Virtual Threads”，不会说“整个服务已经虚拟线程化”。如果真要做到后者，难点通常不在改一个 `ExecutorService`，而在：

- 框架级线程模型怎么接管
- 驱动和客户端在虚拟线程下是否存在 pinning 或兼容问题
- 背压、超时、连接池、监控口径是否一起调整

所以这件事不能只改一个执行器就宣称完成。

## 7. 项目边界与欠缺

### 为什么现在不建议再把这个项目叫“多 Agent 平台”

因为它现在更准确的定位，是“文档驱动的智能知识库问答系统”或者“RAG + Graph + Kafka 增量更新的工程化知识服务”，而不是真正意义上的多 Agent 协作平台。

当前项目里虽然有 `DocParserAgent`、`KnowledgeExtractAgent`、`KnowledgeUpdateAgent`、`QAAgent` 这些模块，但它们更像是按职责拆开的业务组件，而不是具有自主协作、规划、路由、共享黑板和动态调度能力的多 Agent 系统。

如果简历上继续写“多 Agent 平台”，面试官最容易从这些点拆穿：

- 没有 agent 间协商或自治编排。
- 没有 planner / router / orchestrator 这类真正的多 Agent 调度中枢。
- 没有共享任务协议、消息协议或多 agent 工具调用体系。

所以更稳的写法不是把词写大，而是把工程能力写准。

### 这个项目现在最不生产级的地方是什么

如果只能选一个最短板，我会选“Kafka 到多存储的一致性与补偿闭环还不完整”。原因是这条链路同时跨 Kafka、Redis、Milvus、Neo4j，多系统边界越多，补偿和一致性问题就越难靠局部技巧彻底解决。

相比之下，状态机是否够重、图谱建模是否够强、QA 评测是否够全，当然也都是短板，但它们更像质量上限问题；而 Kafka 补偿闭环更像底层工程可靠性问题。

为什么这轮没有一起补完？因为这不是一个“多写几个 if/else”能解决的点，它往往需要更完整的设计，比如：

- 更明确的补偿策略
- 对账和修复流程
- 更强的 replay 控制
- 可能的 outbox / saga / reconcile 机制

这超出了这轮“补工程骨架”的范围。

### 这次补的内容里，哪些可以稳写在简历上，哪些不能写太满

我认为现在可以稳写在简历上的能力包括：

- 轻量工作流状态机编排
- Kafka 增量更新链路的幂等、顺序保护和 chunk diff 局部更新
- 向量检索 + 图谱检索双路融合问答
- 结构化降级信息与 workflow 状态输出
- Java 21 Virtual Threads 在业务子任务中的接入

不建议写太满的内容包括：

- “完整补偿平台”
- “完整生产级 exactly-once”
- “学习排序混排系统”
- “完整图算法检索”
- “全服务虚拟线程化”
- “多 Agent 平台”

如果面试官要代码证据，我最先会举这 3 个实现点：

- `IngestWorkflowService + WorkflowExecutionContext`：能证明状态机、降级和重试统计不是口头设计。
- `KnowledgeUpdateAgent.shouldSkipEvent + handleModify`：能证明 Kafka 增量更新不是只会消费消息，而是有幂等、顺序和局部更新。
- `QAAgent.hybridRerank + QaWorkflowService`：能证明 QA 混合检索、降级和结构化结果输出是真的做了。

### 如果再给我一周，我下一步最想补什么，优先级怎么排

如果只按工程闭环优先级排，我会这样排：

1. Kafka 失败补偿与对账修复能力
2. QA 离线评测和权重校准
3. 图谱身份建模与实体对齐增强
4. 观测性补强，包括阶段耗时、失败分类和告警视图

为什么不是继续堆新功能？因为当前这版最需要的已经不是“再多一个能力点”，而是把已有主链路补得更稳、更可证。我的思路会更偏工程闭环，而不是功能扩张。

### 如果流量上来，这个系统最先可能炸的是哪一层，为什么

如果只能挑一个最容易先出问题的层，我会选外部 LLM 调用这一层。原因很简单：

- 抽取阶段会 fan-out 到多个 chunk。
- QA 生成本身也依赖模型。
- 外部模型最容易受到延迟抖动、限流和配额影响。

Milvus、Neo4j、Kafka、Redis 当然也可能成为瓶颈，但从“最先炸”的概率看，外部模型通常是最脆弱、最贵、最受限的依赖。

如果只能先加一个保护措施，我会优先加更明确的并发上限、超时和熔断/限流保护，尤其是在抽取链路和问答生成链路上。理由是：先把最脆弱的上游保护住，系统整体才能先活下来。

## 8. 过程反思：这次最困难的事情是什么，怎么解决的

如果面试官问“你做这个项目过程中最困难的事情是什么”，我不会回答成某个具体 bug，而会回答成一个更真实的工程难题：**如何把一条跨多个外部系统的 happy path 链路，收敛成一套边界清楚、失败可解释、不会过度包装的工程骨架。**

这个项目同时碰到了好几类典型难点：

- 流程很多，但不能上来就过度设计成重框架。
- 存储很多，但做不到跨系统事务。
- 需要降级，但又不能把故障伪装成正常空结果。
- 需要讲亮点，但又不能把边界吹成“完整生产级”。

我最后的解法，不是追求某一个点极致复杂，而是把系统拆成几个明确问题分别处理：

- 用轻量状态机把流程边界和非法迁移约束住。
- 用统一 `WorkflowStepRunner` 把重试语义和统计口径收拢。
- 用 `EventProcessingStore` 把 Kafka 的事件状态、payload、版本和时间戳落下来。
- 用 chunk diff 和 chunk 级删除把局部更新做出来。
- 用显式异常和结构化降级字段，把“故障”和“空结果”分开。
- 对还没做到的部分，比如 exactly-once、完整补偿平台、学习排序和强图推理，明确承认边界，不做虚假承诺。

如果要把这个过程再总结成一句更适合面试的话，我会说：

> 这次最难的不是把功能堆出来，而是把多个系统之间的状态、幂等、顺序、降级和证据边界统一成一套讲得清楚、测得到、出问题能定位的工程闭环。我的解决思路不是一口气上重框架，而是先把最关键的契约和边界收敛清楚，再决定哪些地方值得继续加重。

这也是我认为这轮改造最有价值的地方：它不只是多了几个功能点，而是让整个项目从“demo 能跑”进一步走向了“工程上能解释、能维护、能继续演进”。
